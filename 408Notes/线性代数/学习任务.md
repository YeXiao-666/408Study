滑动窗口（双指针）的核心逻辑是：**右指针不断扩张寻找可行解，左指针根据条件收缩以寻求最优解。** 滑动窗口生效的一个隐性前提是**单调性**。例如，寻找“和大于等于某一正数的子数组”（全为正数时，窗口越大和越大，单调递增），左指针知道什么时候该停下。

但在这道题中，元素是 `1` 和 `-1`，前缀和是忽大忽小的。如果你当前的窗口内 0 和 1 数量不相等，左指针应该向右移动吗？不一定。也许右指针再往右走一步加入一个字符，窗口内就平衡了。因为**失去了单调性**，左右指针的移动条件变得无法确定，强行使用滑动窗口会导致漏解或逻辑混乱。

#### 滑动窗口 (Sliding Window)

* **解题特点：** 维护一个由左右指针 `[left, right]` 构成的“窗口”。右指针主动向右滑动探索，左指针在窗口不满足条件或寻找更优解时被动向右滑动。可以将 $O(N^2)$ 的嵌套循环优化为 $O(N)$。

* **典型应用场景：**
  
  * **连续子数组/子串**的极值问题（最长/最短）。
  
  * **具有单调性**的条件限制：如“求数组中和 $\ge S$ 的最短连续子数组”（前提是数组全为非负数）。
  
  * 字符串匹配与频次限制：如“无重复字符的最长子串”、“找到字符串中所有字母异位词”。

## 后缀表达式（逆波兰表达式） ： 单栈法

### 一、核心原理

逆波兰表达式将运算符放在操作数之后，天然**无括号**且**严格遵循从左到右的计算顺序**。

**计算规则**：

1. 遇到**操作数**：直接压入栈。

2. 遇到**运算符**：从栈中弹出所需数量的操作数（二元运算符弹出两个，一元弹出一个），计算结果，再将结果压入栈。

3. 遍历结束后，栈顶元素即为整个表达式的值。

**关键性质**：

* 任何有效后缀表达式，计算过程中栈不会下溢，结束时栈中恰好剩下一个元素。

* 操作数的相对顺序与中缀表达式一致，运算符的出现顺序即为实际执行顺序。

## 带括号的表达式计算（+-*/） 双栈法 (Two-Stack Approach)

**核心思想**：使用两个栈——`nums`（操作数栈）和 `ops`（运算符栈）。扫描表达式时，通过比较当前运算符与 `ops` 栈顶运算符的优先级来决定是否计算。

### 二、 算法深度剖析与适用场景

#### 1. 插入排序 (Insertion Sort)

* **优点：** 代码极简；在数据**近乎有序**时，时间复杂度可退化为惊人的 O(N)；这是一种“在线算法”（可以边接收数据边排序）。

* **缺点：** 面对完全无序的大规模数据时，效率极低 (O(N²))。

* **适用场景：**
  
  * 数据量极小（通常 N < 32 或 64）。
  
  * 数据已经基本有序。
  
  * **工程应用：** 几乎所有高级排序算法（如 QuickSort、TimSort）在数据规模缩小到阈值底端时，都会切换为插入排序。

#### 2. 选择排序 (Selection Sort)

* **优点：** 唯一一个**数据交换次数恒定为 O(N)** 的排序算法。

* **缺点：** 无论数据怎样，哪怕已经排好序，它也傻乎乎地扫描 O(N²)，效率极低；且不稳定。

* **适用场景：**
  
  * 极其罕见。仅在**内存写入/交换操作成本极高**（例如写入 Flash 闪存）的极特殊嵌入式场景下可能会被考虑。

#### 3. 归并排序 (Merge Sort)

* **优点：** 性能稳定，永远都是 O(N log N)；且是**稳定排序**。

* **缺点：** 需要 O(N) 的额外内存空间（用于合并），合并操作涉及大量内存拷贝。

* **适用场景：**
  
  * **外部排序：** 当数据量太大，内存装不下，需要对磁盘文件进行排序时。
  
  * 链表排序（对链表归并无需额外空间）。
  
  * 严格要求稳定性的对象级排序。

#### 4. 快速排序 (Quick Sort)

* **优点：** 尽管平均是 O(N log N)，但它的常数项极小。它在内存中是连续跳跃的，**缓存命中率（Cache Locality）极高**，因此在大多数真实场景中，它是处理基本数据类型最快的算法。

* **缺点：** 不稳定；如果基准值没选好（比如在数组已经有序时），会退化为 O(N²) 且可能导致递归爆栈。

* **适用场景：**
  
  * 绝大多数无需保证稳定性的通用排序场景。
  
  * **工程应用：** C++ STL 中的 `std::sort` 核心骨架就是快排。

#### 5. 堆排序 (Heap Sort)

* **优点：** 融合了快排和归并的优点——既能保证最坏 O(N log N) 的时间，又不需要额外空间（原地排序 O(1)）。

* **缺点：** 缓存极度不友好。父节点和子节点在数组中的跨度随着树的变大而变大，导致经常发生 Cache Miss；同样的数据，堆排常数级比快排慢很多。

* **适用场景：**
  
  * **内存空间极其紧张**且要求严格时间上限的嵌入式系统。
  
  * **Top-K 问题**（比如在 10 亿个数里找最大的 100 个，用容量为 100 的小顶堆是最佳方案）。

#### 6. 基数排序 (Radix Sort)

* **优点：** 非比较型排序，突破了比较排序 O(N log N) 的理论下限，速度极快。

* **缺点：** 局限性太强，只能排整数、字符串等可以“按位切分”的数据；需要大量额外空间。

* **适用场景：**
  
  * 海量数据且数据特征明显（如排序 1 亿个 11 位的手机号码，或者 IP 地址）。

#### 7. TimSort

* **优点：** 结合了插入排序的局部高效和归并排序的稳定分治。完美适应真实世界中“部分数据早已排好序”的客观规律。最好情况 O(N)，最坏 O(N log N)，且稳定。

* **缺点：** 实现极为复杂（涉及 Run 的划分、Galloping Mode 飞奔模式、栈平衡等）；仍需额外的内存空间。

* **适用场景：**
  
  * **现代语言的对象排序标配：** Python (`list.sort`)、Java (`Arrays.sort` 处理对象时)、Swift、Rust 的默认排序引擎。因为对象排序通常要求“稳定”，且对象数据往往天然存在局部有序性。

# GC算法

###### 为什么要使用GC呢？也可以说是为什么要使用内存自动管理？有下面的几个原因：

　　1、提高了软件开发的抽象度；

　　2、程序员可以将精力集中在实际的问题上而不用分心来管理内存的问题；

　　3、可以使模块的接口更加的清晰，减小模块间的偶合；

　　4、大大减少了内存人为管理不当所带来的Bug；

　　5、使内存管理更加高效。

　　总的说来就是GC可以使程序员可以从复杂的内存问题中摆脱出来，从而提高了软件开发的速度、质量和安全性。（防止人为原因导致的内存泄漏或野指针的出现，包括内存越界等失误的风险）。



* **提高抽象度与专注力：** 程序员无需再纠结底层的内存字节分配，可以将全部精力集中在业务逻辑的实现上。

* **降低耦合与 Bug 率：** 自动接管内存后，模块间的接口变得更加清晰，彻底消除了“谁分配，谁释放”的争议，大幅减少了由于人为疏忽导致的内存泄漏 Bug。

* **全局优化：** 现代 GC 算法在运行时的内存整理效率，在宏观上往往优于错综复杂的手动内存分配。

###### **什么是GC**

GC如其名，就是垃圾收集，当然这里仅就内存而言。Garbage Collector（垃圾收集器，在不至于混淆的情况下也成为GC）以应用程序的root为基础，遍历应用程序在Heap上动态分配的所有对象[2]，通过识别它们是否被引用来确定哪些对象是已经死亡的、哪些仍需要被使用。已经不再被应用程序的root或者别的对象所引用的对象就是已经死亡的对象，即所谓的垃圾，需要被回收。这就是GC工作的原理。为了实现这个原理，GC有多种算法。比较常见的算法有Reference Counting，Mark Sweep，Copy Collection等等。目前主流的虚拟系统.NET CLR，Java VM和Rotor都是采用的Mark Sweep算法。



### 二、 四大主流垃圾回收算法深度剖析

GC 的核心工作只有两步：**找出垃圾**、**清理垃圾**。围绕这两点，诞生了以下四种主流算法。

###### **1. 引用计数算法 (Reference Counting)**

* **工作原理：** 每个对象自身携带一个“计数器”。如果有其他变量引用它，计数器加 1；引用断开时，计数器减 1。一旦计数器归 0，系统立刻将其回收。

* **优点：** 实时性极高，内存释放平滑，不会造成程序明显的停顿（无需 Stop-The-World）。

* **缺点：** 无法解决“循环引用”问题（对象 A 引用对象 B，对象 B 也引用对象 A，导致两者计数器永远不为 0，成为内存黑洞）。且频繁更新计数器会消耗大量 CPU 资源。

###### **2. 标记-清除算法 (Mark-Sweep)**

* **工作原理：** 分为两阶段。首先是“标记”，GC 从程序的根节点（Roots）出发，顺藤摸瓜遍历所有可达的对象，并打上存活标记。随后是“清除”，遍历整个堆内存，将没有打标记的对象直接判定为垃圾并释放。

* **优点：** 完美解决了循环引用的问题。

* **缺点：** 清除后会留下大量不连续的“内存碎片”，导致后续分配大对象时找不到足够的连续空间。

###### **3. 复制算法 (Copying Collection)**

* **工作原理：** 将内存空间一分为二，每次只使用其中一半。当这一半满了，GC 会将存活的对象连续、紧密地“复制”到另一半空白内存中，然后直接把原来那半块内存全部清空。

* **优点：** 极大地提高了分配速度（指针碰撞），且完全消除了内存碎片。

* **缺点：** 空间利用率极低，直接浪费了 50% 的内存容量。

###### **4. 标记-压缩/整理算法 (Mark-Compact) —— .NET 的基石**

* **工作原理：** 同样先执行“标记-清除”的标记阶段。但在清理时，它并不直接抹除垃圾，而是将所有存活的对象向内存的一端“滑动/压缩”，使它们重新连续排列，然后清理掉边界之外的内存。

* **优点：** 既消除了内存碎片，又不需要像复制算法那样浪费一半的空间。

* **缺点：** 性能开销极大。由于对象在内存中的物理位置发生了移动，GC 必须挂起所有线程，并去修复程序中所有指向这些对象的指针（包括栈指针、寄存器指针等）。

详细流程：

![9e748dff-aadf-4959-acd9-3fdb67556687](file:///C:/Users/DELL/Pictures/Typedown/9e748dff-aadf-4959-acd9-3fdb67556687.png)

Heap内存经过回收、压缩之后，可以继续采用前面的heap内存分配方法，即仅用一个指针记录heap分配的起始地址就可以。主要处理步骤：将线程挂起→确定roots→创建reachable objects graph→对象回收→heap压缩→指针修复。可以这样理解roots：heap中对象的引用关系错综复杂（交叉引用、循环引用），形成复杂的graph，roots是CLR在heap之外可以找到的各种入口点。

GC搜索roots的地方包括全局对象、静态变量、局部对象、函数调用参数、当前CPU寄存器中的对象指针（还有finalization queue）等。主要可以归为2种类型：已经初始化了的静态变量、线程仍在使用的对象（stack+CPU register） 。 Reachable objects：指根据对象引用关系，从roots出发可以到达的对象。例如当前执行函数的局部变量对象A是一个root object，他的成员变量引用了对象B，则B是一个reachable object。从roots出发可以创建reachable objects graph，剩余对象即为unreachable，可以被回收 。

![2149e7f0-fd8f-496b-9fe7-8c14e1183b77](file:///C:/Users/DELL/Pictures/Typedown/2149e7f0-fd8f-496b-9fe7-8c14e1183b77.png)

指针修复是因为compact过程移动了heap对象，对象地址发生变化，需要修复所有引用指针，包括stack、CPU register中的指针以及heap中其他对象的引用指针。Debug和release执行模式之间稍有区别，release模式下后续代码没有引用的对象是unreachable的，而debug模式下需要等到当前函数执行完毕，这些对象才会成为unreachable，目的是为了调试时跟踪局部对象的内容。传给了COM+的托管对象也会成为root，并且具有一个引用计数器以兼容COM+的内存管理机制，引用计数器为0时，这些对象才可能成为被回收对象。Pinned objects指分配之后不能移动位置的对象，例如传递给非托管代码的对象（或者使用了fixed关键字），GC在指针修复时无法修改非托管代码中的引用指针，因此将这些对象移动将发生异常。pinned objects会导致heap出现碎片，但大部分情况来说传给非托管代码的对象应当在GC时能够被回收掉。

###### 5.Generational 分代算法

程序可能使用几百M、几G的内存，对这样的内存区域进行GC操作成本很高，分代算法具备一定统计学基础，对GC的性能改善效果比较明显。将对象按照生命周期分成新的、老的，根据统计分布规律所反映的结果，可以对新、老区域采用不同的回收策略和算法，加强对新区域的回收处理力度，争取在较短时间间隔、较小的内存区域内，以较低成本将执行路径上大量新近抛弃不再使用的局部对象及时回收掉。分代算法的假设前提条件：

　　1、大量新创建的对象生命周期都比较短，而较老的对象生命周期会更长；

　　2、对部分内存进行回收比基于全部内存的回收操作要快；

　　3、新创建的对象之间关联程度通常较强。heap分配的对象是连续的，关联度较强有利于提高CPU cache的命中率，.NET将heap分成3个代龄区域: Gen 0、Gen 1、Gen 2；

![f4678b03-a46f-4f89-bc1e-a38d5997091e](file:///C:/Users/DELL/Pictures/Typedown/f4678b03-a46f-4f89-bc1e-a38d5997091e.png)

Heap分为3个代龄区域，相应的GC有3种方式: # Gen 0 collections, # Gen 1 collections, #Gen 2 collections。如果Gen 0 heap内存达到阀值，则触发0代GC，0代GC后Gen 0中幸存的对象进入Gen1。如果Gen 1的内存达到阀值，则进行1代GC，1代GC将Gen 0 heap和Gen 1 heap一起进行回收，幸存的对象进入Gen2。

　　2代GC将Gen 0 heap、Gen 1 heap和Gen 2 heap一起回收，Gen 0和Gen 1比较小，这两个代龄加起来总是保持在16M左右；Gen2的大小由应用程序确定，可能达到几G，因此0代和1代GC的成本非常低，2代GC称为full GC，通常成本很高。粗略的计算0代和1代GC应当能在几毫秒到几十毫秒之间完成，Gen 2 heap比较大时，full GC可能需要花费几秒时间。大致上来讲.NET应用运行期间，2代、1代和0代GC的频率应当大致为1:10:100。

###### 6.Finalization Queue和Freachable Queue

        这两个队列和.NET对象所提供的Finalize方法有关。这两个队列并不用于存储真正的对象，而是存储一组指向对象的指针。当程序中使用了new操作符在Managed Heap上分配空间时，GC会对其进行分析，如果该对象含有Finalize方法则在Finalization Queue中添加一个指向该对象的指针。

　　在GC被启动以后，经过Mark阶段分辨出哪些是垃圾。再在垃圾中搜索，如果发现垃圾中有被Finalization Queue中的指针所指向的对象，则将这个对象从垃圾中分离出来，并将指向它的指针移动到Freachable Queue中。这个过程被称为是对象的复生（Resurrection），本来死去的对象就这样被救活了。为什么要救活它呢？因为这个对象的Finalize方法还没有被执行，所以不能让它死去。Freachable Queue平时不做什么事，但是一旦里面被添加了指针之后，它就会去触发所指对象的Finalize方法执行，之后将这个指针从队列中剔除，这是对象就可以安静的死去了。

　　.NET Framework的System.GC类提供了控制Finalize的两个方法，ReRegisterForFinalize和SuppressFinalize。前者是请求系统完成对象的Finalize方法，后者是请求系统不要完成对象的Finalize方法。ReRegisterForFinalize方法其实就是将指向对象的指针重新添加到Finalization Queue中。这就出现了一个很有趣的现象，因为在Finalization Queue中的对象可以复生，如果在对象的Finalize方法中调用ReRegisterForFinalize方法，这样就形成了一个在堆上永远不会死去的对象，像凤凰涅槃一样每次死的时候都可以复生。

###### 9.复制收集算法

原理
为了解决标记清除算法的效率问题，一种称为“复制”(Copying)的收集算法出现了，它将可用内存按容量划分为大小相等的两块，每次只使用其中的一块。当这一块的内存用完了，就将还存活着的对象复制到另外一块上面，然后再把已使用过的内存空间一次清理掉。这样使得每次都是对其中的一块进行内存回收，内存分配时也就不用考虑内存碎片等复杂情况，只要移动堆顶指针，按顺序分配内存即可，实现简单，运行高效。
缺点
同时只有一半的内存被使用（根据实际情况可以采用非1:1的比例划分，如HotSpot的新生代8:1:1）

###### 8.GC注意事项：

       （1）只管理内存，非托管资源，如文件句柄，GDI资源，数据库连接等还需要用户去管理。
       （2） 循环引用，网状结构等的实现会变得简单。GC的标志-压缩算法能有效的检测这些关系，并将不再被引用的网状结构整体删除。
       （3）GC通过从程序的根对象开始遍历来检测一个对象是否可被其他对象访问，而不是用类似于COM中的引用计数方法。
       （4） GC在一个独立的线程中运行来删除不再被引用的内存。
       （5）GC每次运行时会压缩托管堆。
       （6）你必须对非托管资源的释放负责。可以通过在类型中定义Finalizer来保证资源得到释放。
       （7）对象的Finalizer被执行的时间是在对象不再被引用后的某个不确定的时间。注意并非和C++中一样在对象超出声明周期时立即执行析构函数
       （8） Finalizer的使用有性能上的代价。需要Finalization的对象不会立即被清除，而需要先执行Finalizer.Finalizer，不是在GC执行的线程被调用。GC把每一个需要执行Finalizer的对象放到一个队列中去，然后启动另一个线程来执行所有这些Finalizer，而GC线程继续去删除其他待回收的对象。在下一个GC周期，这些执行完Finalizer的对象的内存才会被回收。
       （9）.NET GC使用"代"(generations)的概念来优化性能。代帮助GC更迅速的识别那些最可能成为垃圾的对象。在上次执行完垃圾回收后新创建的对象为第0代对象。经历了一次GC周期的对象为第1代对象。经历了两次或更多的GC周期的对象为第2代对象。代的作用是为了区分局部变量和需要在应用程序生存周期中一直存活的对象。大部分第0代对象是局部变量。成员变量和全局变量很快变成第1代对象并最终成为第2代对象。
      （10） GC对不同代的对象执行不同的检查策略以优化性能。每个GC周期都会检查第0代对象。大约1/10的GC周期检查第0代和第1代对象。大约1/100的GC周期检查所有的对象。重新思考Finalization的代价：需要Finalization的对象可能比不需要Finalization在内存中停留额外9个GC周期。如果此时它还没有被Finalize，就变成第2代对象，从而在内存中停留更长时间。

### 三、 .NET CLR 的 GC 核心机制

在 .NET 平台中，超过 80% 的资源是托管资源（分配在 Managed Heap 上）。.NET 的 GC 机制主要基于**标记-压缩 (Mark-Compact)** 算法，并结合了**分代 (Generational)** 策略进行深度优化。

**1. 根对象 (Roots) 与可达性** CLR 的 GC 通过寻找 Roots 来构建可达对象图 (Reachable Objects Graph)。Roots 的范围非常广泛：

* 全局对象与已经初始化的静态变量。

* 当前线程堆栈（Stack）和 CPU 寄存器中正在使用的局部变量。

* 传递给非托管代码的 Pinned Objects（固定对象，这类对象在 GC 压缩阶段不可移动，否则会导致非托管代码指针失效）。

* 终结队列（Finalization Queue）中的对象。

**2. Generational 分代算法** 为了解决 Mark-Compact 扫描全堆成本过高的问题，.NET 引入了统计学假设：**大量新创建的对象很快就会死亡，而活得越久的对象越倾向于继续存活。** 因此，托管堆被划分为三个代（Generations）：

* **第 0 代 (Gen 0)：** 包含最新分配的局部变量。大小通常只有几兆，存满即触发回收。速度极快（几毫秒）。幸存者晋升为 Gen 1。

* **第 1 代 (Gen 1)：** 作为缓冲地带。如果 Gen 1 存满，会同时回收 Gen 0 和 Gen 1。幸存者晋升为 Gen 2。Gen 0 和 Gen 1 的总大小通常控制在 16MB 左右。

* **第 2 代 (Gen 2)：** 包含长生命周期的对象（如全局变量、静态数据）。大小可能高达数 GB。触发 Gen 2 回收被称为 Full GC，成本极高，会引起明显的程序停顿。

* **触发频率：** 在健康的程序中，第 0、1、2 代的回收频率大约应为 100 : 10 : 1。

### 四、 终结器、复生与非托管资源释放

GC 只能管理内存，无法管理**非托管资源**（如文件句柄、数据库连接、GDI 句柄等）。为了应对这一问题，.NET 提供了双重保障机制。

**1. Finalization Queue 与 Freachable Queue（系统兜底机制）** 当对象被 `new` 且包含析构函数（`Finalize` 方法）时，CLR 会将其指针放入 **Finalization Queue**。当该对象成为垃圾时，GC 不会立刻销毁它，而是将其移动到 **Freachable Queue**。这一步叫做**复生（Resurrection）**。随后，CLR 会启动一个专门的后台线程去执行这些对象的 `Finalize` 方法，执行完毕后，该对象才会在下一次 GC 周期中被真正回收。 **代价：** 带有终结器的对象至少需要在内存中多停留一个甚至多个 GC 周期，极大地拖慢了回收效率。



**2. IDisposable 接口与标准 Dispose 模式（确定性资源释放机制）** 鉴于垃圾回收器（GC）执行时机的非确定性，以及终结器（Finalizer）运行带来的额外性能开销，C# 引入了 `IDisposable` 接口，赋予开发者显式且及时释放非托管资源（如网络句柄、数据库连接）的能力。

* **`using` 语句（生命周期管控）：** 例如 `using (var conn = new SqlConnection()) { ... }`。该语法糖在编译时会被安全地展开为 `try-finally` 结构，从而确保无论业务逻辑正常执行还是抛出异常，在代码作用域结束时，必定会立即、可靠地调用 `Dispose()` 方法。

* **`GC.SuppressFinalize(this)`（终结器豁免）：** 这是标准 Dispose 模式中极其重要的一环。当开发者通过主动调用 `Dispose()` 完成资源的清理后，必须调用此方法。它从底层通知 GC：该对象的非托管资源已手动释放，请将其引用从终结队列（Freachable Queue）中移除。这避免了对象在垃圾回收时被强制复生（Resurrection）并经历低效的终结流程，极大优化了内存回收的性能。它会告诉 GC：“我已经打扫干净了，请把这个对象从 Finalization Queue 中移除，不要再去走那一套低效的复生和终结流程了。”

* 一般不需要程序员手动调用**GC.SuppressFinalize(this)**，因为调用webRequest.Dispose();  时，webRequest类内部的是实现IDispose接口的方法里会自动调用<u>`GC.SuppressFinalize(this)</u>

### 五、 开发者视角的 GC 注意事项总结

结合上述底层原理，在日常开发中需要牢记以下准则：

* **职责边界：** GC 负责内存，你负责非托管资源（文件、Socket、数据库）。

* **网状结构优势：** 不要害怕复杂的对象循环引用，基于可达性分析的 GC 能够轻松将其整体识别并回收。

* **非实时性：** GC 运行在独立线程，触发时间不确定。千万不要依赖析构函数来执行对时间敏感的清理工作。

* **压缩代价：** 每次完整的 GC 运行都会移动对象并压缩内存，请尽量减少极大对象的频繁分配以避免内存碎片和昂贵的指针修复。

* **慎用析构函数：** 除非万不得已作为忘调 `Dispose` 的安全网，否则不要定义 Finalizer。它不仅会降低回收效率，还可能导致对象意外复生。

* **谨慎干预：** 尽管可以使用 `GC.Collect()` 强制执行垃圾回收，但这通常会打破 CLR 自动优化的节奏，导致未成熟的对象被提前提升到 Gen 2，进而引发更严重的性能瓶颈。
  
  

# Unity的GC策略与算法

### 一、 为什么操作系统有了回收策略，软件还要自己做？

操作系统的内存管理和软件的内存管理，面临的**“粒度和上下文”**完全不同。

1. **粒度太粗：** 操作系统管理内存是以**页（Page）**为单位的（通常是 4KB）。当你写代码 `new Player()` 时，可能只需要几十个字节。如果每次申请或释放几十个字节都要向操作系统报告，这种“微操”会让操作系统崩溃。

2. **上下文缺失：** 操作系统不知道什么是“玩家”、什么是“子弹”、它们之间谁引用了谁。它只知道分配给这个进程一块内存，进程死掉时整块收回。如果运行中内存不够了，操作系统只会简单粗暴地把不常用的内存页塞进硬盘（Swap/虚拟内存），或者直接触发 OOM（Out of Memory）杀掉进程。

3. **系统调用开销大：** 频繁地向操作系统申请内存需要跨越“用户态”到“内核态”，开销极大。

**因此，软件的做法是：** 软件启动时，先向操作系统“批发”一大块连续的内存（Heap 堆），然后在软件内部自己建立一套账本，进行“零售”和“回收”。这就是软件自带内存管理器的原因。

* * *

### 二、 Unity 的双层内存架构

Unity 是一个 C++ 和 C# 混合的引擎，因此它的内存管理天然分为两大阵营：

1. **Native Memory (非托管内存 / C++ 层)：**
   
   * **负责：** 引擎底层逻辑、渲染管线、物理引擎、音频、纹理贴图（Texture）、网格（Mesh）等。
   
   * **回收策略：** **手动分配与释放**。这部分内存没有自动垃圾回收，当场景切换或显式调用 `Destroy()`、`Resources.UnloadUnusedAssets()` 时，引擎底层的 C++ 代码会精准地释放（`free` / `delete`）这些内存。

2. **Managed Memory (托管内存 / C# 层)：**
   
   * **负责：** 开发者写的游戏业务逻辑，也就是各种 C# 脚本中的类实例、字符串、数组等。
   
   * **回收策略：** **垃圾回收器（Garbage Collector, GC）自动接管**。这也是导致游戏卡顿的“万恶之源”，我们需要深入探究它的算法。

* * *

### 三、 深入 Unity 托管内存的回收算法 (GC)

Unity 的托管环境（无论是过去的 Mono 还是现在的 IL2CPP（IL2CPP (Intermediate Language To C++）））主要采用的是一种被称为 **Boehm-Demers-Weiser GC** 的变体。我们来深入拆解它的核心机制：

#### 1. 核心算法：标记-清除 (Mark-and-Sweep)

这是 Unity GC 的基础。当系统发现堆内存不够用，或者开发者手动调用 `GC.Collect()` 时，就会触发这个过程，分为两步：

* **标记阶段 (Mark)：**
  GC 会找到所有的 **GC Roots（根节点）**（以应用程序的root为基础），通常包括静态变量、当前执行栈上的局部变量等。然后，像顺藤摸瓜一样，沿着对象的引用链遍历。凡是能被访问到的对象，都被标记为“存活”。

* **清除阶段 (Sweep)：**
  遍历整个堆内存。那些**没有被标记**的内存块，就会被认定为“死亡”（即没有任何变量再引用它们了）。GC 会将这部分内存的标记抹除，并把它们重新加入到“空闲内存链表”中，供下次分配使用。时间复杂度为 $O(N)$，其中 $N$ 是堆的总大小。

#### 2. 致命弱点：不压缩 (Non-compacting) 与 内存碎片化

很多现代语言（如 Java 或是纯 .NET 环境）的 GC 会在清除后做一步“压缩（Compact）”——把活着的积木推到一边，让空闲的空间连成一片。

**但 Unity 的默认 GC 是“不压缩”的。** 这导致了一个非常严重的后果：**内存碎片（Fragmentation）**。

* _举例：_ 假设你的内存里交替存放着“活对象”和“死对象”，GC 回收后，内存变得像蜂窝煤一样，全是小窟窿。此时你申请一个大数组，虽然总的空闲内存够用，但找不到一块**连续**的巨大空间。

* _结果：_ Unity GC 会认为内存不足，从而向操作系统申请**扩大堆内存**。更糟的是，Unity 的托管堆内存是**“只增不减”**的，扩大后的内存很难再还给操作系统，导致游戏占用内存越来越大。

#### 3. 性能杀手：Stop-The-World (STW)

传统的标记-清除过程必须在一个绝对静止的环境下进行。为什么？因为如果 GC 正在“顺藤摸瓜”地标记存活对象，而你的游戏逻辑同时在修改引用（比如把武器从左手换到了右手），GC 就会标错，导致活对象被误杀。

因此，触发 GC 时，**Unity 会暂停主线程上所有正在执行的游戏逻辑**，直到 GC 结束。如果堆内存很大，这个停顿可能长达几十到上百毫秒，玩家就会明显感觉到“卡顿（掉帧）”。

#### 4. 现代进化：增量式垃圾回收 (Incremental GC)

为了解决 STW 带来的严重卡顿，Unity 在较新的版本中引入了**增量式 GC**（目前已是默认选项）。

* **算法思路：** 既然一次性做完太耗时，那就把 GC 的工作切碎（Slicing），分摊到多个渲染帧中去完成。每帧只花 1~2 毫秒做一点标记工作，然后继续跑游戏逻辑。

* **写屏障技术 (Write Barrier)：** 核心难点在于解决前面提到的“GC进行中引用发生改变”的问题。增量 GC 引入了写屏障——当游戏逻辑在 GC 期间修改了某个对象的引用关系时，写屏障会立刻记录下这个变动（将其标记为“脏”），GC 在最后阶段只需重新检查这些变动过的对象即可，极大缩短了绝对暂停的时间。

* * *

### 四、 现实与对策：为什么还要开发者自己管理？

虽然 Unity 有了自动 GC，但在实时渲染的游戏领域（要求每秒 60 次甚至 120 次稳定循环），依靠底层的 GC 依然是不够的。开发者必须在应用层建立自己的“回收/重用”策略：

1. **对象池 (Object Pool)：** 对付碎片化和 GC 触发的最有效手段。怪物死亡时不 `Destroy()`，而是隐藏（`SetActive(false)`）并放回池子；刷新时再拿出来。**核心思想是用“状态重置”代替“内存的释放和重新分配”。**

2. **值类型 (Struct) 优先：** C# 中的 Class 分配在堆（Heap）上，归 GC 管；而 Struct（如 Vector3, Quaternion）分配在栈（Stack）上，随函数结束立即由 CPU 指针回收，完全不产生 GC 垃圾。

3. **拥抱 Native 内存 (Job System & ECS)：** Unity 近年推出的 DOTS 架构，允许开发者使用 `NativeArray` 等结构。这些内存直接从 C++ 层（Native Memory）分配，由开发者手动 `Dispose()` 释放，完全绕过了 C# GC，实现了极致的性能。

总结来说，操作系统管宏观，软件管微观。Unity 的内存回收策略建立在 C++ 的手动管理和 C# 的（增量式）标记清除算法之上。而真正顶尖的游戏性能，往往诞生于开发者对这套底层规则的深刻理解与巧妙规避之中。

## CLR工作原理（Common Language Runtime，公共语言运行时）

我们可以把 CLR 想象成一个“超级大管家”，它不仅负责把代码翻译成机器能懂的语言，还包揽了后勤（内存）、调度（线程）和安保（安全验证）工作。

### 一、 CLR 的运行机制：从代码到机器码的“两步走”战略

CLR 的运行机制最核心的特点是**“二次编译”**。这与 C++ 的直接编译成机器码，或 Python 的纯解释执行都不同。

1. **第一步：编译期（源代码 -> 中间语言 IL）** 无论你使用的是 C#、F# 还是 VB.NET，各自的语言编译器（如 Roslyn）首先会将源代码编译成一种通用的、与硬件无关的语言，称为 **IL（Intermediate Language，中间语言）**。与此同时，编译器还会生成**元数据（Metadata）**，里面详细记录了代码中定义的所有类、方法、属性等描述信息。IL 和元数据被打包成一个程序集（.dll 或 .exe）。

2. **第二步：运行期（中间语言 IL -> 本地机器码）** 当你运行这个程序集时，CLR 正式介入。此时，CLR 内部的 **JIT（Just-In-Time，即时编译器）** 会发挥作用。它会在方法_第一次被调用时_，读取 IL 代码和元数据，并根据当前运行的底层操作系统和 CPU 架构（如 x86, ARM64），将其“即时”编译成高度优化的**本地机器码（Native Code）**。编译好的机器码会被缓存起来，后续再次调用该方法时，将直接执行机器码，无需再次编译，从而保证了极高的运行效率。

* * *

### 二、 CLR 的三大核心服务

把代码跑起来只是基础，CLR 的强大在于它提供了一个受管（Managed）的运行环境。

#### 1. 内存管理（Garbage Collection, 垃圾回收）

在 C/C++ 中，程序员需要手动 `new` 和 `delete` 内存，稍有不慎就会导致内存泄漏或野指针。CLR 通过引入 **GC（垃圾回收器）** 接管了这一切。

* **托管堆（Managed Heap）：** 当代码中创建引用类型（Class）的对象时，CLR 会在一个连续的内存区域（托管堆）中为其分配空间。

* **代际回收（Generational GC）：** CLR 的 GC 将对象分为三代（Generation 0, 1, 2）。
  
  * **第 0 代：** 新创建的对象。这部分内存区域较小，GC 发生最频繁，清理速度极快（因为大多数对象“朝生夕死”，如局部变量）。
  
  * **第 1 代：** 在第 0 代回收中存活下来的对象，作为缓冲。
  
  * **第 2 代：** 长生命周期的对象（如全局缓存）。这里的数据最稳定，GC 触发频率最低，但一旦触发（Full GC），耗时也最长。

* **压缩与碎片整理：** GC 在清理掉“死亡”对象后，会自动把存活的对象挤压到一起，消除内存碎片，保持内存分配的高效（这就需要 CLR 自动更新所有指向这些对象的指针）。

#### 2. 线程调度（Thread Scheduling）

虽然线程是由操作系统（OS）底层提供的，但跨平台或跨操作系统的线程管理非常复杂。CLR 对此进行了抽象和优化：

* **托管线程池（Managed Thread Pool）：** CLR 维护着自己的线程池。开发者在使用 `Task` 或 `ThreadPool.QueueUserWorkItem` 时，实际上是在向 CLR 申请线程。CLR 会根据当前 CPU 的负载和队列长度，智能地增加或销毁工作线程，避免了操作系统频繁创建/销毁线程带来的巨大上下文切换开销。

* **托管与非托管映射：** CLR 中的一个 `System.Threading.Thread` 对象在底层通常映射到一个操作系统的原生线程，但 CLR 会监控这些线程的运行状态，处理跨线程的同步上下文（SynchronizationContext）。

#### 3. 代码安全验证（Code Safety Verification）

在 JIT 将 IL 编译为机器码的过程中，CLR 会执行严格的安全检查（Verification）：

* **类型安全（Type Safety）：** CLR 会检查代码是否试图进行非法的类型转换（比如把一个 Dog 对象强行当作数据库 Connection 对象来用）。

* **内存访问安全：** 它会验证代码有没有越界访问数组，或者试图读取未经初始化的内存。如果检测到危险操作，JIT 会拒绝编译并抛出 `InvalidProgramException`。这就从根本上杜绝了 C/C++ 中常见的缓冲区溢出攻击。

* * *

### 三、 消除语言隔离墙：CTS 与 CLS

如果仅仅有 IL，不同语言还是无法顺畅交流。比如，C# 里的整型叫 `int`，VB.NET 里叫 `Integer`，C++ 里有无符号整型（`unsigned int`），而某些语言根本没有无符号整型的概念。如果 C# 写了一个库，VB.NET 怎么调用？

CLR 通过制定两套标准彻底解决了这个问题：

#### 1. CTS (Common Type System, 公共类型系统)

CTS 是 .NET 世界里的**“万法之源”**。

* 它定义了所有数据类型的根基（例如所有的类最终都继承自 `System.Object`）。

* 它规定了值类型（Value Types，如结构体、枚举，存在栈上）和引用类型（Reference Types，如类、接口，存在堆上）的本质区别。

* **作用：** 无论你是用哪种语言，只要在 .NET 平台上运行，底层的类型都是统一的。C# 的 `int` 和 VB.NET 的 `Integer`，在编译后统一变成了 CTS 中定义的 `System.Int32`。这就保证了类型在内存级别的绝对互通。

#### 2. CLS (Common Language Specification, 公共语言规范)

虽然 CTS 定义了所有的类型，但并非所有语言都能支持 CTS 里的**所有**特性。比如，C# 区分大小写（`var Name` 和 `var name` 是两个变量），但 VB.NET 是不区分大小写的。如果 C# 开发者写了一个类，里面暴露了两个公开属性，一个叫 `Age`，一个叫 `age`，VB.NET 开发者去调用时就会彻底崩溃，不知道该调哪个。

* **什么是 CLS？** CLS 是 CTS 的一个**子集**。它提取了各种 .NET 语言交集中的最低标准。

* **作用（跨语言互操作的契约）：** 如果你希望你用 C# 编写的类库能够被所有其他 .NET 语言（如 F#、VB.NET）无缝调用，你在编写**公开（Public）的 API** 时，就必须遵守 CLS 规范。例如：
  
  * 不要在公开 API 中使用无符号类型（如 `UInt32`），因为并非所有语言都支持。
  
  * 不要仅靠字母大小写来区分不同的公共方法或属性。

**总结：** CTS 确保了底层类型在内存和逻辑上的一致性，而 CLS 则是不同语言开发者握手言和的“外交协议”。结合 CLR 强大的编译（JIT）、内存（GC）和安全管理，共同铸就了今天高效、安全且高度跨语言的 .NET 生态。
